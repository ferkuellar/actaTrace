# Phase 4 — Document Storage and Integrity Pipeline

## 1. Phase Objective

Phase 4 designs and implements the ActaTrace document handling layer. Documents are stored outside blockchain, PostgreSQL stores metadata, and SHA-256 hashes provide tamper-evident integrity verification.

The system now supports:

- Secure acta file uploads.
- SHA-256 hash generation.
- S3-compatible object storage through MinIO/AWS S3-compatible APIs.
- Local storage provider for development and tests.
- Document metadata registration.
- File integrity verification.
- Optional future IPFS support placeholder.
- Blockchain hash comparison through the Phase 3 provider facade.
- Tamper-evident document lifecycle events.

Phase 4 does not store full files on blockchain, does not implement electronic voting, and does not expose sensitive internal storage paths publicly.

## 4. Storage Design Principles

- Documents are stored in object storage, not blockchain.
- PostgreSQL stores metadata, not binary files.
- Blockchain stores only document hashes.
- File hash is generated before final document registration.
- Hash is immutable after registration.
- Every upload, retrieval, verification, mismatch, and access denial creates an audit log.
- Storage providers are interchangeable.
- Public users never see raw internal storage paths.
- Access to documents is role-controlled.
- Retrieval uses presigned URLs or controlled local development URLs.

## 5. Storage Strategy

Storage uses Strategy and Adapter patterns.

`StorageProvider` defines:

- `upload_file(file_bytes, object_key, content_type)`
- `get_file(object_key)`
- `generate_presigned_url(object_key, expires_in)`
- `file_exists(object_key)`
- `delete_file(object_key)`

### 5.1 LocalStorageProvider

Used for development and pytest. It writes files below `LOCAL_STORAGE_PATH` and prevents object-key path traversal.

### 5.2 S3StorageProvider

Used for AWS S3, MinIO, or compatible providers through boto3. It supports upload, retrieval, existence checks, deletion, and presigned URL generation.

### 5.3 IPFSStorageProvider Placeholder

Included as a clean placeholder. It intentionally raises configuration errors because production IPFS integration is out of Phase 4 scope.

## 6. Object Key Strategy

Object keys are generated server-side.

Format:

```text
actas/{election_year}/{state}/{municipality}/{polling_station_code}/{acta_id}/{document_id}.pdf
```

Rules:

- Original filename is not used as the primary storage key.
- Path components are sanitized.
- Object keys avoid personal or sensitive data.
- Original filename is stored only as metadata.
- Object keys are unique.
- Object keys are generated by `DocumentStorageService`.

## 7. Hash Generation Pipeline

`HashService` supports:

- `generate_sha256_from_bytes(content: bytes) -> str`
- `generate_sha256_from_stream(stream) -> str`
- `generate_sha256_from_file(path: str) -> str`
- `verify_sha256(content: bytes, expected_hash: str) -> bool`

Rules:

- Hashes are lowercase hex.
- Hash is generated before final document registration.
- Stored `sha256_hash` must not be modified.
- Re-hashing is supported for verification.
- Hash mismatch marks the document as `MISMATCH` and emits `DOCUMENT_HASH_MISMATCH`.

## 8. Document Lifecycle

Integrity statuses:

- `PENDING`
- `VALID`
- `MISMATCH`
- `CORRUPTED`
- `STORAGE_MISSING`
- `ANCHORED`

Access statuses:

- `PRIVATE`
- `PUBLIC_VERIFIABLE`
- `RESTRICTED`

Lifecycle statuses:

- `UPLOADED`
- `HASHED`
- `STORED`
- `VERIFIED`
- `ANCHORED`
- `ARCHIVED`

Allowed transitions:

- `UPLOADED -> HASHED -> STORED -> VERIFIED -> ANCHORED`
- `STORED -> VERIFIED`
- `VERIFIED -> ANCHORED`
- Any active state -> `ARCHIVED` through a controlled workflow.

Forbidden transitions:

- `ARCHIVED -> STORED` without a formal reopening workflow.
- Direct modification of `sha256_hash`.
- Public access when `access_status != PUBLIC_VERIFIABLE`.
- Marking a document `VERIFIED` when the current file hash does not match the database hash.

## 11. API Endpoints

Base path:

```text
/api/v1/documents
```

### 11.1 Upload Acta Document

```text
POST /documents/upload-acta
```

Multipart form-data:

- `file`
- `acta_id`
- `polling_station_id`
- `document_type`
- `notes` optional

Flow:

1. Authenticate user.
2. Validate role: `ADMIN_ELECTORAL`, `CAPTURISTA`, or `SUPERVISOR`.
3. Validate file type and size.
4. Read file safely.
5. Generate SHA-256 hash.
6. Check duplicate hash.
7. Generate storage key.
8. Upload to storage provider.
9. Register document metadata in PostgreSQL.
10. Link document to acta.
11. Create audit logs.
12. Optionally trigger blockchain anchoring if configured.
13. Return document metadata and hash.

### 11.2 Retrieve Document Metadata

```text
GET /documents/{document_id}
```

Returns metadata only. Public users should not receive raw storage internals in future public endpoints.

### 11.3 Download / View Document

```text
GET /documents/{document_id}/download
```

Rules:

- Authorized roles can download.
- Public users can download only when `access_status = PUBLIC_VERIFIABLE`.
- Response returns a presigned or controlled local URL.
- Bucket credentials are never returned.

### 11.4 Verify Document Integrity

```text
POST /documents/{document_id}/verify-integrity
```

Flow:

1. Fetch metadata.
2. Retrieve file from storage.
3. Recompute SHA-256.
4. Compare with stored hash.
5. If blockchain anchor exists, compare with blockchain record.
6. Update integrity status.
7. Create audit log.
8. Return verification result.

### 11.5 Verify Against Blockchain

```text
GET /documents/{document_id}/verify-blockchain
```

Flow:

1. Get document hash.
2. Query blockchain provider.
3. Compare anchored hash.
4. Return verification proof.

### 11.6 List Documents

```text
GET /documents
```

Filters:

- `integrity_status`
- `access_status`
- `uploaded_by`
- `acta_id`
- `polling_station_id`
- `date_from`
- `date_to`

## 19. Documentation Notes

### Storage Strategy

Storage is provider-based. The backend can use local disk, MinIO, AWS S3, or another S3-compatible provider without changing document domain logic.

### Why Files Are Not Stored On Blockchain

Files are too large, sensitive, and operationally risky to replicate to ledger peers. The blockchain stores only hashes and proof metadata.

### How SHA-256 Integrity Works

The system hashes file bytes at upload time and stores the digest in PostgreSQL. Later verification retrieves the stored object, re-hashes it, and compares the result to the database hash and blockchain proof when available.

### How Hashes Are Compared

Verification compares:

1. File hash from current storage bytes.
2. Database hash in `documents.sha256_hash`.
3. Blockchain hash from Phase 3 provider.

### How To Configure MinIO Locally

Run:

```bash
cd actatrace-backend
docker compose up -d --build --remove-orphans
docker compose exec backend alembic upgrade head
```

MinIO bucket creation is handled by `minio-init`.

### How To Configure S3-Compatible Storage Later

Set:

```env
STORAGE_PROVIDER=s3
S3_ENDPOINT_URL=
S3_ACCESS_KEY=
S3_SECRET_KEY=
S3_BUCKET_NAME=
S3_REGION=
S3_USE_SSL=true
```

Use IAM or managed secrets in production. Do not commit real credentials.

### Known Limitations of Phase 4

- Public document portal is not implemented.
- IPFS is a placeholder only.
- No OCR extraction.
- No multi-region storage.
- No advanced DLP scanning.
- Local URLs are development-only.
- S3 bucket policies must be hardened in real deployments.
